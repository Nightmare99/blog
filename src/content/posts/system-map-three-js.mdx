The portfolio behind this blog isn't a hero image with some floating shapes bolted on — the background *is* the navigation. Scroll progress drives a camera through a 3D node graph, and each node is a section of the site. I wanted it to read as a "system map": nodes are services, edges are connections, and small packets travel between them like distributed traces.

Here's how the pieces fit together.

## A camera on rails, not a camera on autopilot

The obvious approach is `OrbitControls` plus some ambient rotation. I didn't want that — I wanted the camera to feel directed, like it's walking a fixed path through infrastructure. So the camera doesn't move freely; it rides a `THREE.CatmullRomCurve3` built from each node's position, and its position along that curve is just the page's scroll progress, clamped to `[0, 1]`.

The trick that made it feel intentional instead of mechanical: the camera doesn't look at itself. It looks slightly *ahead* on the curve:

```ts
const camT = clamp(progress, 0, 0.985)
const lookT = clamp(progress + 0.06, 0, 1)
```

That six-percent lead means the next node is always drifting into frame before you reach it, which reads as anticipation instead of arrival. A small sine-based lateral offset keeps nodes in three-quarter view instead of dead center, and everything is `lerp`'d toward its target rather than snapped — position at `0.045`, look-target at `0.06` — so scroll jitter gets absorbed instead of transmitted straight to the camera.

## Nodes that know when they're being looked at

Each node is an icosahedron core, a slightly larger wireframe shell rotating against it, and a flat ring that idles at low opacity. When a node's section is the active one (tracked in a small Zustand store that Lenis keeps in sync with scroll), the ring starts pulsing and the core eases up to 1.15x scale. Nothing snaps — every state change is a `lerp` toward a target, which is really the theme of this whole scene: few things happen instantly, most things *drift* toward where they should be.

## Packets as an InstancedMesh, not N meshes

The moving dots that travel along each edge — meant to read as request traffic between services — are the one place raw mesh count would have mattered. Three packets per edge, one edge per pair of adjacent nodes: at even a modest node count that's a lot of individual spheres if done naively, and I don't want the fans on someone's laptop to notice a portfolio site is running.

Instead, all packets are a single `InstancedMesh`. Every frame, each instance recomputes its position by lerping between its edge's two endpoints using a per-instance offset and speed (so packets aren't all synchronized), writes the result into `dummy.matrix`, and the mesh's `instanceMatrix` is flagged dirty once at the end of the loop rather than per-instance. One draw call for however many packets are in flight.

## What I'd change

The scroll-to-progress mapping is currently linear, which means densely-packed sections and sparse ones get the same amount of camera travel. A version keyed to section *height* rather than raw scroll percentage would probably feel more consistent — that's the next thing on the list, along with cutting the point light per node down to something cheaper once there are enough nodes for it to matter.
